This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

SIGER (antes SIGER A; Nexbyte, Defensoria de la Ninez de Chile) es un monolito Spring Boot 4.1.1 / Java 25 con el frontend React 19 + TypeScript 6 + Vite 8 empaquetado dentro del mismo JAR. Usa MySQL independiente en la VM y H2 para pruebas locales. Los nombres internos (paquete `cl.nexbyte.sigera`, esquema `siger_a_*`, raiz `D:\SIGER-A`, namespace `SIGER-A-2026`, cookie `SIGERA_SESSION`) se conservan por compatibilidad; lo visible dice SIGER. El consumidor PULL/ACK del Formulario (manual o automatico), el correo Graph y el servicio Windows existen pero estan inactivos salvo configuracion explicita (ver abajo). La documentacion y los mensajes al usuario estan en espanol.

## Comandos

Las herramientas son portables y viven en `.tools/` (`java25`, `apache-maven-3.9.11`, `node-v24.22.0-win-x64`). No se instalan globalmente ni se modifican PATH ni JAVA_HOME de forma persistente. Si faltan, ejecutar `scripts\Get-Tools.ps1`.

```powershell
# Build completo: chequea scripts, npm ci + tsc + vite build, Maven clean verify (con tests) y genera release\SIGER-<fecha>.zip
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Build.ps1 -IncludeJava
#   -SkipChecks omite los tests (un build asi no acredita pruebas)

# Ejecutar en local (requiere backend\target\siger-a.jar): perfil local, H2 en var\local-db, http://localhost:18543
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\Run-Local.ps1
```

Para iterar sin pasar por Build.ps1, en una sesion de PowerShell:

```powershell
$env:JAVA_HOME='C:\siger-a\.tools\java25'; $env:PATH="C:\siger-a\.tools\node-v24.22.0-win-x64;$env:JAVA_HOME\bin;$env:PATH"
.\mvnw.cmd -B -ntp -f backend\pom.xml test                                   # todos los JUnit
.\mvnw.cmd -B -ntp -f backend\pom.xml test -Dtest=RulesTest                  # una clase
.\mvnw.cmd -B -ntp -f backend\pom.xml test -Dtest=Attention040Test#metodo    # un metodo
cd frontend; npm run typecheck   # tsc --noEmit (no hay linter configurado)
cd frontend; npm run build       # genera frontend\dist
cd frontend; npm run dev         # Vite en 127.0.0.1:5173, proxy de /api a 127.0.0.1:18543 (el backend debe estar corriendo)
```

`backend/pom.xml` copia `../frontend/dist` a `static/` en la fase `process-resources`. Por eso hay que ejecutar `npm run build` antes de `mvnw package`; si no, el JAR queda sin la UI o con una version anterior.

Los tests usan `@SpringBootTest` + `@ActiveProfiles("test")` (H2 en memoria `MODE=MySQL`, Flyway activo, sin semillas). `WorkflowTest` inserta por SQL su propio organigrama, cuentas y grants sinteticos y ejecuta comandos con `flow.run(...)`. Los que usan `siger.seed-demo=true` necesitan un nombre de H2 propio y `siger.data=./target/...-${random.uuid}`: el bootstrap no sobrescribe un `bootstrap-usuarios.csv` existente y fallaria al repetir sin `clean`.

## Arquitectura

El backend es un solo paquete plano `cl.nexbyte.sigera`, sin capas JPA ni entidades: SQL directo mediante `Db` (envoltorio de JdbcTemplate que devuelve `Map<String,Object>` con claves en minusculas, con helpers estaticos `n/s/b/nullableId`). El SQL debe funcionar igual en H2 `MODE=MySQL` y en MySQL.

**Toda escritura de negocio pasa por `POST /api/commands` → `Workflow.run`.** El comando es `{key: UUID, type, id, revision, data}`. Dentro de una sola transaccion, `run`:
1. toma un lock global (`Db.lock()`: `SELECT ... FROM operation_lock FOR UPDATE`);
2. resuelve el `Actor` desde la sesion (nunca desde el cliente) y bloquea si `must_change`;
3. aplica idempotencia con `command_log`: la misma clave y el mismo hash devuelven el resultado previo, y la misma clave con otros datos es un conflicto;
4. despacha por `type` al servicio del dominio: `IntakeCommands` (COM_*, SOL_*, LINK_*), `RequirementCommands` (REQ_*, FLOW_*, REOPEN_*), `CaseCommands` (CASE_*, NOTE_RECTIFY, TASK_*), `Attention` (ATTENTION_*), `Personnel` (STAFF_/GRANT_/SCOPE_/SUBSTITUTE_*, PROFILE_SET, DOC_RELEASE; HOLIDAY_* delega en `Holidays` y CATALOG_* en `StatCatalogs`);
5. registra el resultado.

Un comando nuevo se agrega al `switch` de `Workflow.run` y al `run()` del servicio de su dominio. Las transiciones compartidas (crear REQ o Caso, asignar, cerrar Caso, constancias, folios, listas de canales, materias y resultados) están en `Lifecycle`; hay que reutilizarlas, no duplicarlas. Las mutaciones usan concurrencia optimista: el cliente envia `revision` y se valida con `Db.revision(row, expected)`. Las acciones relevantes se registran con `db.audit(...)` en `audit_event`. El frontend reutiliza la misma `key` al reintentar una operacion incierta.

Las lecturas usan endpoints GET en `Api.java`: `Queries` (detalle autorizado, catalogo, workspace, administracion) y `BoardQueries` (bandejas paginadas `POST /worklist/{kind}` con `{page,size,q,filter,scope}` en el cuerpo desde G08c, contadores, dashboard). Los conteos se limitan siempre al alcance del actor.

**Permisos (`Access`)**: un `Actor` tiene `grants` (rol + ambito `org_scope`) vigentes. Una subrogancia activa traslada temporalmente al subrogante los grants del titular, en los mismos ambitos, y el titular conserva su cartera personal como PROFESIONAL. `actor(username)` y `enabledActors()` comparten `resolve()`. Para avisar o filtrar a "todos los que cumplen X" se usa `enabledActors()` o `notifyWhere`/`notifyReceivers`/`notifyHeads`, nunca un bucle de `actor()` por cuenta: corre dentro del lock global. Hay helpers como `head(scope)`, `professional(scope)`, `registrar(scope)` y `solReceiver(...)`. Los roles concedibles, con su alcance (ambito o institucional) y grupo, estan en el catalogo unico `Roles` (publicado en `/api/catalog` como `roles`). Desde 0.5.0 (gate G01) TI concede y revoca funciones (una a una o con el perfil completo `PROFILE_SET`, gate G02: diferencia por rol y ambito, revision = `staff.security_version`, un solo epoch) y administra subrogancias (`Personnel`), no combina TI con otras funciones y la instancia conserva al menos una TI permanente; AUTORIDAD ya no tiene efecto. Desde G05, `CONSULTA_INSTITUCIONAL` (institucional, `Actor.institutionalReader()`) lee todas las fichas COM, SOL, REQ, CAS y FLUJO, la primera atencion (NNA y versiones), la proyeccion del Formulario y los documentos no reservados (`Access.reqRecords` = registro completo del REQ). No ve constancias ni documentos reservados salvo por otra funcion y ninguna regla de escritura la considera: lo prueba `InstitutionalReaderTest`, con un barrido de todos los comandos de `Workflow.run`. Desde G06 tambien `BoardQueries.Visibility` (`institutional`) le abre todas las bandejas de expedientes (COM, SOL de todo estado, REQ, Casos, flujos y atenciones; tareas y avisos siguen siendo personales), Inicio le muestra la seccion `institutional` (reemplaza a "Resumen de mi alcance") y la ficha entrega `institutional_read` cuando la cuenta la lee solo por la consulta (`Queries.readable` con `Actor.withoutInstitutionalReader()`). Los filtros que piden una decision propia (`sol:pending`, `sol:returned`, `cas:review`, `flujos:incoming`...) llevan su condicion de rol: el permiso de la bandeja ya no basta para acotarlos. La equivalencia `Access` vs `BoardQueries` en las 8 bandejas esta en `InstitutionalReaderTest.bandejasEquivalentesAAccess`; `menuFor` se prueba en `frontend/tests/menu.test.ts`. Sedes regionales (R01, V11): `org_scope` tiene `region_code` (codigo del Formulario, `AdultIdentity.REGIONS`), `state` PROYECTADA/ACTIVA/CERRADA coherente con `enabled`, `opens_ms` y `revision`. TI las administra con `SCOPE_CREATE`/`SCOPE_UPDATE`/`SCOPE_ACTIVATE`/`SCOPE_CLOSE` (`Personnel.closeBlockers`); las cuentas y funciones admiten sedes PROYECTADA (`Access.staffableScope`: dotacion preparada que rige al activar) y nunca CERRADA, y una sede no recibe `JEFATURA` nueva: la Coordinacion regional es `DIRECCION` de la sede (rutina `Bootstrap.convertRegionalHeads`, marcador `COORDINACION_REGIONAL_050`; aviso `JEFATURA_EN_SEDE`). `Access.receiverOf`/`destination` es la regla unica de destino de SOL, flujos y entregas a jefatura y el catalogo publica por ambito `level`, `state` y `receives` (todas las sedes, tambien proyectadas y cerradas) y `regions`. Una sede cerrada sigue legible: las lecturas no usan `access.scope` (que exige `enabled`). No se siembran sedes reales en codigo ni migraciones. Lectura nacional por materia (R02, D9): `Actor.matters()` (calculado en `resolve` desde las `DIRECCION` vigentes, propias o subrogadas, en la raiz central de UPR, UPD o UEP) abre solo en sedes, en `Access` (`matterSol`, `matterReq`, `matterCase`, `matterCom`, `reqWideRead`) y en `Visibility.byMatter`: por la materia sugerida de la SOL o la del REQ, la cadena completa (COM y originales, primera atencion, registro del REQ y flujos); por la del Caso, solo el Caso y el resumen del REQ (`caseSourceDocuments` no la considera). La ficha entrega `matter_read` (`Actor.withoutMatters()`). `COM_ROUTE`/`SOL_ROUTE` aceptan `suggested_matter` solo hacia una sede, `SOL_ASSUME` la copia al REQ y `REQ_MATTER` (cabeza del principal, solo sedes) la rectifica. Toda verificacion de permiso se hace en el servidor; el frontend (`lib/access.ts: has/headAt`) solo decide que botones mostrar. Desde G04 la interfaz de funciones es el perfil de cada cuenta (`features/admin/ProfileDialog.tsx`, logica pura en `profile.ts` con `tests/profile.test.ts`): reenvia el termino exacto en milisegundos de cada funcion que no cambia y su inicio solo si es programada; no hay boton de concesion individual (`GRANT_CREATE` sigue en el servidor). **Errores**: `Problem(status, mensaje)`. `Problem.require` → 409, `Problem.denied()` → 403. `ApiErrors` devuelve `{message}`, audita las denegaciones 403/404, responde 405 (con `Allow`) a un metodo no admitido y 415 a un formato no admitido, y nunca registra SQL, URLs ni datos ciudadanos en el log. Los mensajes van en espanol y son visibles al funcionario. `Input` valida la entrada (`text(key,max,required)`, `id`, `choice`, `instant`, `reason`) y no acepta estado, autor ni rol enviados por el navegador.

**`Rules`**: reglas de cierre puras (cierre de Caso por nivel o jefatura, cierre de REQ, derivacion), cubiertas por `RulesTest`. Solicitar termino (`Rules.closeRequest`, responsable) y confirmar el cierre (`Rules.closure`) son facultades distintas: la ficha del Caso expone `can_request_close`/`close_request_blockers` aparte de `can_close`/`closure_blockers`, y el frontend no debe inferir una de la otra. El origen del REQ (`solicitation_id` nulo = primera atencion directa; en el Caso, `req_origin`) se toma del servidor.

**`Attention`** (0.4.0): primera atencion progresiva sobre COM+REQ. **Comunicaciones externas (Formulario Publico via SMR)**: `Workflow.conserveExternal` es una entrada interna (no es un comando de `run()`; `/api/commands` la rechaza para cualquier sesion), y conserva el original sin descargar sus adjuntos. `ExternalOriginal.parse` valida el contrato (reglas portadas de `EntregaCompleta.validar` de SMR), recalcula huellas y verifica el sello Ed25519 con `FormularioKeys` (`siger.formulario-trusted-keys`; sin claves se rechaza todo) antes de escribir. El texto firmado queda inmutable en `communication_original`; `ExternalProjection` calcula una vez, al crear, la COM (sin textos de procedencia) y `external_person`/`external_attribute`/`external_field` (procedencia, discrepancias, diccionario SRCeI, edad al ingreso). Un reenvio idempotente no reproyecta. La ficha COM entrega la proyeccion solo tras `comForRead`, nunca el JSON original.

**Consumidor del Formulario (PULL/ACK, V8)**: inactivo salvo `siger.formulario.pull.enabled=true` y `run-once=true` en un proceso sin web y con `siger.scheduling=false` (`FormularioPull`, lanzado solo por `scripts/Invoke-FormularioPull.ps1`); sin planificador, endpoint ni comando de funcionario. `FormularioConsumer` hace un ciclo: concilia ACK pendientes, reclama una entrega (`FormularioClient`: HTTPS, sin redirecciones, Bearer solo al origen), valida con `ExternalOriginal.parse`, custodia los originales por streaming con tamano y SHA-256 firmados (`Documents.custodyExternal`, clave derivada de UUID), y `FormularioReception.register` crea en un COMMIT la COM, los `document_item` INGRESO en cuarentena (+ `external_document`), el comprobante `FormularioAck` y la reserva con ACK pendiente (`formulario_reception`). Confirma solo tras el COMMIT y una nueva verificacion de la custodia; despues del COMMIT nunca informa fallo. La version del ACK sigue al canal (NNA 1.1, publico 1.0). Registra con la identidad tecnica `sistema:formulario-publico` (`staff.technical`): sin sesion, sin funciones, fuera de listas y de la administracion de cuentas. El folio del comprobante exige `siger.folio-prefix` `[A-Z][A-Z0-9]{1,15}`. Solo un consumidor por cola: el de SMR debe estar detenido (no lo verifica SIGER). Contrato del Formulario verificado en 0.8.0 (E00): los vectores NNA con el RUN del presentador de fuente `SRCEI` y nivel `CONTRASTADO_EN_FUENTE` (nota contractual del 15/11/2026; copia y huellas de formulario-web `6f886eb` en `src/test/resources/formulario/`, con `PROCEDENCIA.txt`) se registran por `conserveExternal` y por la recepcion PULL/ACK sin elevar la procedencia a autenticacion (`FormularioSrceiContractTest`, `FormularioSrceiReceptionTest`); las huellas de `territorio.json` y `paises.json` del servidor y del frontend se comparan con las del Formulario (`frontend/tests/formularioCatalogs.test.ts`). ## Reglas de dominio que no deben romperse

La fuente de verdad es `docs/DECISIONES_FUNCIONALES.md`; el alcance y lo pendiente estan en `docs/ALCANCE_Y_PENDIENTES.md`. Los invariantes clave son:
- La cadena es COM (lo recibido) → SOL (a una jefatura) → REQ (nace al asumir la SOL) → Caso(s) bajo el mismo REQ. Un ingreso externo por clasificar no crea REQ ni Caso.
- La primera atencion directa crea COM+REQ en un solo acto, sin SOL ni Caso. Entregar no transfiere la jefatura principal ni crea un Caso. Para dar seguimiento, la jefatura abre un Caso en el mismo REQ.
- La complejidad se asigna por REQ (BAJA/MEDIANA/ALTA), y no tener clasificacion no equivale a BAJA. El profesional solo cierra Casos BAJA; los demas niveles pasan a revision de jefatura. El subrogante no confirma su propio Caso.
- Una tarea no terminal bloquea el cierre del Caso. Cerrar un Caso no cierra el REQ, que la jefatura principal cierra de forma expresa.
- Una derivacion aceptada crea el sucesor y cierra el origen en la misma transaccion. Una colaboracion crea un Caso paralelo. Una transferencia cambia solo al principal.
- Los roles son concesiones dentro de un ambito. TI no obtiene acceso a expedientes por administrar cuentas, y la historia conserva al actor real.
